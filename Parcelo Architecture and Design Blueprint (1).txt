Parcelo: Architecture and Design Blueprint
The build plan for Parcelo, a logistics platform for booking, orders, shipments, dispatch,
last-mile delivery, fleet and inventory

Version 2.0 | 10 November 2026

Parcelo is three small React apps (customer, ops dashboard and driver) that share one
Firebase backend, built in three phases: Phase 1 lets customers book and track deliveries,
Phase 2 adds dispatch and drivers, and Phase 3 adds inventory, messages and reports.
This document explains how it is put together, what every screen does, and exactly what
to build in each phase.

1. The Big Picture

1.1 What Parcelo does
A customer books a delivery and sees the price. The business assigns a driver and vehicle.
The driver delivers and uploads proof. Everyone can follow the package with a tracking
number.

Reading it: the apps read data straight from the Firestore database, and the data updates
live on screen. Anything that must be protected, such as booking, assigning a driver,
changing a status or reducing stock, goes through a Cloud Function that checks who you
are and applies the rules. Security rules are the last line of defence on every read and
write.

1.4 The journey of one package
1. The customer fills in pickup, drop-off and package details and sees a price. (Phase 1)
2. The customer confirms. The system creates the order and a shipment with a tracking

number and the status Pending. (Phase 1)
3. The dispatcher assigns a driver and vehicle: Assigned. (Phase 2)
4. The driver picks up the package: In Transit, then Out for Delivery. (Phase 2)
5. The driver delivers and uploads a photo: Delivered. (Phase 1 by admin, Phase 2 by

driver)
6. The customer follows every step on the tracking page. (Phase 1)
7. Stock goes down when product orders are placed, and messages are sent at each

step. (Phase 3)

Example: the customer taps Confirm booking in the Customer app.

1. The page checks the form is complete.
2. api/orders.js  calls the bookDelivery  Cloud Function through the shared

functions.js  helper. The login is sent automatically.
3. The function checks the user is a logged-in customer and that the quote has not

expired. It works out the price again itself, so it cannot be tampered with.
4. In one step it creates the order, the shipment with a new tracking number, the first

status entry and the public tracking record.
5. It answers with the tracking number and the page shows the success screen.
6. The Ops dashboard's order list updates live, because it listens to the same orders.

Why a separate publicTracking  collection? A Firestore document is read whole, so
fields cannot be hidden. The public tracking page therefore reads a small safe copy (no
names, phone numbers or full addresses). The rules let anyone get one record by its
tracking number but not list them all, so numbers cannot be browsed.
How they connect: one customer has many orders; one order has one shipment; one
shipment has many events and, from Phase 2, one driver and one vehicle. Documents
point to each other by id.

2.5 Statuses
A status may only move along the arrows. The backend refuses any other move.

SHIPMENT   Pending -> Assigned -> In Transit -> Out for Delivery -> Delivered
              |                                       |
              |                                       +-> Failed -> (try 
again) Out for Delivery
              +-> Cancelled   (only while still Pending)

ORDER      Placed -> Confirmed -> Shipped -> Delivered        (or Cancelled)

PAYMENT    Unpaid -> Paid
           Unpaid -> Pending Transfer -> Paid

In Phase 1 there is no driver yet, so the admin moves a shipment straight from Pending to
In Transit. The Assigned step switches on in Phase 2.

2.8 How the apps talk to Firebase
There are two ways an app uses the backend.

1. Reading data: the app asks Firestore directly (for example "my orders"). The result
updates live. The security rules decide who may read what.

2. Actions that must be protected: the app calls a Cloud Function (for example "book
this delivery"). The function checks who you are, applies the rules and writes the data.
Apps are not allowed to write these records directly.

The tables in each phase list the operations the apps need, written like web addresses
(such as POST /api/orders ). Use this table to see how each one is built in Firebase.

3.5 Working out the price

price = (base fee + price per km x distance + price per kg x weight) x size 
factor

base fee = N1,500    per km = N120    per kg = N100
size factor: small 1.0 | medium 1.2 | large 1.5

Worked example: 12 km, 3 kg, medium. (1,500 + 1,440 + 300) x 1.2 = 3,888, rounded to the
nearest N50 = N3,900.

change them without touching code.

4.5 How it works, step by step
Assigning a job

1. A new booking appears on the dispatch board as Pending.
2. The dispatcher picks a free driver (the list shows who is nearest to the pickup) and a

free vehicle, then taps Assign.
3. The server does all of this in one go, or none of it: checks the shipment is Pending, the

driver is available and the vehicle is available; saves the driver and vehicle on the
shipment; sets the status to Assigned; marks the driver on job and the vehicle in use.

4. If any check fails the server answers with a 409 message and nothing changes. This is
what stops two dispatchers giving the same driver two jobs.

5. The job appears on the driver's phone.

Doing the job
1. The driver taps Start Delivery: the status becomes In Transit.
2. The driver taps Out for Delivery when starting the last leg: the status changes and

location sharing starts.
3. The driver takes the proof photo and taps Delivered. If the customer is not there, the

driver taps Failed and gives a reason.
4. When the job ends, the server frees the driver and vehicle and stops location sharing.

Live location

1. While the status is Out for Delivery, the phone sends its position about every 20
seconds ( POST /api/drivers/:id/location ).

2. The server keeps the latest position. The dispatcher and the customer who owns the
order see the marker move.

3. The public tracking page does not show the position.

Reassigning
If a driver cannot continue, the dispatcher uses Reassign. The old driver and vehicle are
freed and the new ones are locked in the same single step. Reassigning is blocked once
the package is out for delivery.

the order.
4. If a product falls to its reorder level or below, it is flagged on the Low stock tab.
5. If the order is cancelled while the shipment is still Pending, the quantities go back up.

Notifications
1. Whenever a shipment gets a new status entry, the server looks up the message for

that event.
2. It sends an SMS or email to the customer, using their chosen channel.
3. It saves a log entry (sent or failed). A failed message is retried up to three times.

5.7 Rules
Stock can never go below zero.
A product order is all or nothing: if one item is short, nothing is booked.
A product is low when quantity <= reorderLevel .
Customers can turn off optional messages, but delivery updates are always sent.
Reports are for admins only and show totals, not personal details.
If online payment is added, an order is marked Paid only after the payment provider
confirms it to the server. The customer's browser returning to the site is never treated
as proof of payment.

5.12 Check that it works
